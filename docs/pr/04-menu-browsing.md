# PR 04 — Menu browsing

The first real page. Guests can browse the menu, filter by category, search, and share or reload the exact view. It also brings the mock API to the browser, so `pnpm dev` shows a working app.

## What changed

- **Menu page** (`/`): category chips, a debounced search box, item cards, skeletons, an error view with Retry, and an empty view with a way out.
- **`useMenuFilters`**: the filters live in the URL (`?category=<id>&q=<text>`), so a view survives a reload and can be shared.
- **`useDebouncedRef`**: a small generic composable for the search box.
- **`CategoryChips`** and **`MenuItemCard`**: presentational, props in and events out.
- **Mock API in the browser**: `public/mockServiceWorker.js` (generated by `msw init`), `src/mocks/browser.ts`, and a switch in `main.ts`. Always on in `pnpm dev`; in a production build only when `VITE_ENABLE_MOCKS=true`.
- **Tests**: composables, components, and `MenuPage` as an integration test against the MSW handlers (loading, filters, URL, debounce, out-of-order responses, empty, errors).

## Why (decisions and trade-offs)

- **The URL is the source of truth for filters.** The page reads `category` and `q` from the route and refetches when they change; nothing about the filters lives only in component state, except the text still being typed, which reaches the URL after the user pauses. Back, forward, reload and shared links all work because they are all just URL changes.
- **Two different history behaviours on purpose.** Choosing a category uses `push` (the back button should undo it). Typing in the search uses `replace`, so a burst of searches does not fill the history with entries. The test pins this: after choosing a category and searching, Back lands on the page before the category.
- **URL to input, without clobbering typing.** When the URL changes from outside (back/forward) the input follows. A URL change the page just wrote itself is recognised (it equals the debounced text) and skipped; otherwise a slow navigation landing while the user keeps typing would overwrite their keystrokes.
- **Race protection comes from `useAsyncState`**: typing "pi" then "pizza" cannot leave the answer to "pi" on screen. The page test stages a slow response for "pi" and a fast one for "pizza" and checks the final list; I confirmed it fails when both defences (abort and the "still current?" check) are removed.
- **Old results stay while new ones load.** Changing a filter dims the current list instead of replacing it with a skeleton, so the page does not flash between keystrokes. The skeleton is only for the first load.
- **Category chips are toggle buttons, not tabs.** They filter a list; they do not switch panels, so `aria-pressed` on buttons in a labelled group is the honest pattern. No arrow-key tab semantics to implement or get wrong.
- **Failing categories do not block the menu.** If only `/categories` fails the dishes still load and an inline "Try again" appears where the chips would be.
- **Images cannot shift the layout.** Each image has `width`/`height` attributes and an `aspect-ratio` box, `loading="lazy"` and `decoding="async"`; an item without an image shows an initial in the same box. `alt=""` because the dish name is right next to it.
- **Phone: rows, desktop: grid.** A card is a compact row with a thumbnail on a phone and a vertical card from tablet width up; the grid goes from 1 to 2, 3 and 4 columns. Chips scroll sideways on a phone and wrap above it. A bug found in the browser: the non-wrapping chip row made the grid column wider than the screen, pushing the search box off the edge; fixed with `minmax(0, 1fr)`.
- **Card has an unavailable state** (dimmed, "Sold out") although the guest API never returns unavailable dishes today; the admin menu (PR 08) and a dish that sells out between loads will need it.
- **Announcements:** the dish count is a `role="status"` line that updates as filters change; loading is announced by `AsyncBoundary`; errors by `role="alert"`.
- **Mock API switch.** `useMocks = import.meta.env.DEV || import.meta.env.VITE_ENABLE_MOCKS === 'true'`. Vite replaces both at build time, so in a real production build the condition is `false` and the whole mock API (handlers, fixtures, MSW) is dropped; I checked the bundle for the mock strings with and without the flag. If the worker cannot start (unsupported browser, blocked), the app still mounts and shows its error states rather than a blank page.
- **One thing to know:** `public/mockServiceWorker.js` is copied into `dist/` even in a production build. It is inert unless something registers it, and the production build never does; excluding it from real builds can be part of the deploy work in PR 10.

## Visual check

Checked in a real Chrome (driven from outside the repo) at 375, 768 and 1280 px in light and dark: the loading skeleton, the full grid, a filtered list, and the empty state. Then a scripted run through the actual flow: typing produced three requests in total instead of one per keystroke, the URL updated without extra history entries, Back, reload with filters and "Clear filters" all behaved.

## Size

About 1100 changed lines excluding the lockfile and the generated worker file, of which about 520 are tests.

## How to verify

```sh
pnpm install
pnpm format:check && pnpm lint && pnpm typecheck && pnpm test && pnpm build
pnpm dev
```

In the browser: type in the search box and watch the Network tab (one request after you pause); pick a category and press Back; reload with filters in the address bar; open `/?q=zzz` for the empty state. The Dev tools panel that slows the network or forces errors comes in PR 09; until then, `setMockConditions` in `src/mocks/conditions.ts` is the hook.

## Review talking points

1. URL as the single source of truth, and the push-versus-replace decision.
2. The two-way sync between input and URL, and the case the "equals the debounced text" check prevents.
3. How the page gets race safety for free from `useAsyncState`, and what the out-of-order test proves.
4. Keeping stale results visible during a refresh, versus the skeleton for the first load.
5. How the mock API is switched on in dev and demo builds and removed from production.
